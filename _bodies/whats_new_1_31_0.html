Releases · 1.31.0

What's new in Capa 1.31.0

A small information-flow security fix. A value marked @secret, captured by a closure and then leaked from inside that closure's own body, used to slip past the checker with no diagnostic at all. This release flags it: a warning by default, and a hard error under @strict_ifc.

← All releases

What this release is

Capa 1.31.0 is an information-flow security fix, and only that. It closes a case where a value you marked @secret could reach a public sink, a log line or a network call, with no signal to the author: no warning at the default tier, and not even an error under @strict_ifc. That silence at both tiers was the whole problem, because the author wrote @secret, believed the value was protected, and it was not.

It is a minor release. The only programs it affects are the ones that were already leaking a secret without a warning; every correct program compiles exactly as before. That follows the same rule the earlier information-flow soundness fixes on the 1.x line used: tightening a static check so a program that was silently unsound now warns is a security fix, not a breaking change.

What changed, in plain terms

A closure is a small inline function that can capture the variables around it. Deferring a log line or a serialise step into a closure and calling it a moment later is an everyday pattern. The leak lived in the order of events:

  • A closure captured a variable that was still public when the closure was written.
  • The @secret value was stored into that variable after the closure was written.
  • The closure was then called, and its body sent the now-secret value to a public sink.

The checker read the closure body once, at the point it was written, when the captured value was still public, and never looked at it again at the call. So the later taint was missed entirely. Each closure now also carries a summary of which captured values reach a sink inside its body. At the call the compiler checks the live label of each of those captured values, and a captured @secret reaching an internal sink is flagged at the call site, on both the interpreter and the Wasm backend.

Before and after

The closure below captures bag, the secret is written into bag afterwards, and the closure sinks it:

leak.capa
type Bag { data: String }

fun leak(stdio: Stdio, secret: @secret String)
    var bag: Bag = Bag { data: "public" }
    let log: Fun() -> Unit = fun() -> Unit => stdio.println(bag.data)
    bag.data = secret        // the secret arrives after log is defined
    log()                    // sinks the secret inside the closure body

On earlier versions capa --check reported ok and exited 0, and even adding @strict_ifc reported no error, while the program printed the secret at run time. Now the default check warns:

terminal
$ capa --check leak.capa
warning: information-flow: a @secret value is passed to 'log' as the
  captured 'bag', which reaches a public sink inside 'log' (it sends
  data out of the program). Route it through
  declassify(value, reason: "...") if this disclosure is intended.

Under @strict_ifc the same finding is a hard error and the build exits non-zero, so a pipeline that gates on strict mode now stops it. If the disclosure is genuinely intended, route the value through declassify(value, reason: "..."), exactly as in the information-flow chapter; a closure that declassifies the value it sinks stays clean.

An honest scope

This is a security fix with a deliberately narrow, disclosed scope. It closes the locally-resolved case: a closure bound to a name and called in the same place, or one that is immediately invoked, where the sink is reached directly or through a named helper. That is the common shape, and it is now covered on both backends.

It does not close every closure shape, and the advisory says so plainly. Still open, and documented as tested residuals, are closures that escape local resolution (aliased to another name, passed to another function and called there, or returned), a sink reached only through a further nested inline closure, and a few container-aliasing shapes. These remain honest, known limitations rather than silent ones. If you want the full list and the reasoning, read the advisory below.

Warnings do not block. As with every information-flow finding in Capa, the default tier warns and the program still runs; it is @strict_ifc that turns the finding into a build-stopping error. Gate on strict mode in CI if you want the guarantee enforced.
